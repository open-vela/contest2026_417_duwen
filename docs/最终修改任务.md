  一、目标

  在 GD32/openvela 上完成真实 ai_agent 集成，并实现两个真实自定义 Skill：

  1. sensor_query
  2. device_control

  形成以下可验证闭环：

  Sensor -> UMCA -> GD32温度缓存
         -> ai_agent调用sensor_query
         -> 现有LlmChatRequest V1
         -> ESP32/MiMo
         -> 现有LlmChatResponse
         -> GD32校验动作建议
         -> ai_agent调用device_control
         -> FanCommand -> Actuator -> FanState

  MiMo只提供文本和动作建议，GD32保持最终授权。

  四、sensor_query Skill

  复用现有GD32温度缓存，不重复向Sensor发起另一套查询。

  输出固定结构，至少包含：

  {
    "available": true,
    "temperature_mC": 31000,
    "age_ms": 420,
    "quality": 0,
    "sensor_online": true
  }

  规则：

  1. online、数据年龄、质量和有效性全部由GD32判断。
  2. 复用现有温度新鲜度阈值，不在新代码中复制另一套阈值。
  3. Sensor离线、数据超龄或质量无效时：
     - available=false；
     - 不向LLM提供可被误认为有效的温度数值。
  4. 使用请求创建时的原子快照，避免读取到字段组合不一致的缓存。
  5. Skill不得阻塞UART或协议线程。
  6. 输出明确日志，但不高频刷屏：

  skill=sensor_query result=ok available=1 age_ms=...
  skill=sensor_query result=unavailable reason=offline|stale|quality

  五、device_control Skill

  复用现有FanCommand -> FanState实现，不复制控制协议。

  只接受：

  - device=fan, state=on
  - device=fan, state=off

  规则：

  1. 检查Actuator在线及会话Boot ID。
  2. 生成独立控制request_id。
  3. 发布FanCommand并等待关联FanState。
  4. 校验Source、Boot ID、request_id和result。
  5. 返回confirmed、offline、timeout、mismatch或rejected。
  6. 只允许0/1，不做隐式类型转换。
  7. 同一风扇命令不得因LLM重试而重复执行。
  8. 调用前仍执行现有GD32安全授权逻辑。
  9. 输出日志：

  skill=device_control requested=on result=confirmed
  skill=device_control requested=off result=timeout

  六、修改现有chat流程

  保留命令：

  umca_gd32 chat <用户问题>

  新流程：

  1. 创建Agent请求及deadline。
  2. 通过ai_agent调用sensor_query。
  3. 使用固定容量缓冲生成紧凑可信上下文。
  4. 通过现有LlmChatRequest V1发送给ESP32。
  5. 接收并校验现有LlmChatResponse。
  6. action=none时只显示文本。
  7. action=set_fan时，通过ai_agent调用device_control。
  8. 显示文本回复和最终执行结果。
  9. 任一步失败都不得产生未经确认的动作。

  发送给MiMo的文本采用确定性模板：

  [TRUSTED_DEVICE_CONTEXT]
  temperature_valid=1
  temperature_mC=31000
  temperature_age_ms=420
  temperature_quality=0
  sensor_online=1
  actuator_online=1
  fan_state=0
  [/TRUSTED_DEVICE_CONTEXT]
  [USER_REQUEST]
  <用户文本>
  [/USER_REQUEST]
  Use only trusted device context. If temperature_valid=0, do not invent a temperature.
  Keep the reply concise. Device action may only be none or set_fan.

  无有效温度时必须生成：

  temperature_valid=0
  sensor_online=<0或1>

  并省略temperature_mC，避免无效旧值进入模型。

  要求：

  1. 固定容量格式化，所有snprintf返回值必须检查。
  2. 按现有V1 Payload实际容量计算用户文本最大长度。
  3. 超长时在发送前明确拒绝，不允许静默截断UTF-8。
  4. 校验用户文本UTF-8；拒绝NUL及非法控制字符。
  5. 不把用户文本放进TRUSTED_DEVICE_CONTEXT区域。
  6. 不把上下文称为实时值，日志注明snapshot_age_ms。
  7. ESP32已经负责限制MiMo text长度；GD32仍必须正确处理非零status。

  七、修复“错误显示为空白”

  当前MiMo响应过长等错误会返回非零status且无正文。GD32不得显示为空回复。

  至少映射为：

  status=0：成功
  status!=0：LLM request failed: status=<值>

  若现有公共头文件已有状态枚举，应显示枚举名称；不得自行改变线级数值。

  错误响应：
  - 不调用device_control；
  - 不显示为成功；
  - stats中增加对应失败计数；
  - 不打印伪造的模型正文。

  八、主动闭环的最小实现

  不要新增自动云端高频调用。

  复用现有温度接收和本地auto控制，增加一个默认关闭的Agent评估开关：

  umca_gd32 agent-auto on
  umca_gd32 agent-auto off
  umca_gd32 agent-auto status

  行为：

  1. 仅在有效温度跨越现有高/低阈值时产生一次评估事件。
  2. 复用现有阈值和迟滞，不复制配置。
  3. 固定容量为1的事件邮箱；已有待处理事件时合并，不堆积。
  4. 设置不少于60秒的冷却时间，避免消耗Token和重复控制。
  5. 默认关闭，重启后保持关闭，不写入持久配置。
  6. 事件处理在线程/工作队列中完成，Sensor回调只投递事件。
  7. 网络、ESP32、MiMo、Sensor或Actuator不可用时：
     - Agent评估失败；
     - 不执行迟到动作；
     - 现有GD32本地auto控制继续正常工作。
  8. Agent动作仍必须经过device_control Skill。
  9. Agent评估使用固定问题：
     “根据可信设备快照判断是否需要开关风扇，简短回答。”
  10. 同一阈值跨越事件不得重复执行。

  如果现有本地auto与agent-auto同时开启：
  - 本地auto拥有更高优先级；
  - Agent不得反向覆盖刚完成的本地安全动作；
  - 最简单实现可以在local auto开启时拒绝开启agent-auto，并明确提示冲突。
  优先采用该互斥方案，避免复杂仲裁。
