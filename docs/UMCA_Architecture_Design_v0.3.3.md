## 1. 引言

### 1.1 背景

当前嵌入式系统在不同应用场景（智能车、机器人、无人机、智能家居等）中采用异构通信方案：板内芯片间使用 SPI/I2C，板间使用 CAN/CAN FD，高速骨干使用以太网/TSN，外设使用 USB，无线使用 WiFi/BLE。这种碎片化带来以下问题：

- **协议碎片化**：不同物理层需要独立的软件栈，增加开发和维护成本。
- **扩展困难**：新增模块需要理解目标系统的具体总线协议和地址分配机制。
- **实时性难以保障**：事件触发总线（如 CAN）存在仲裁饥饿风险，缺乏跨物理层的统一 QoS 体系。
- **互操作性差**：模块间无法直接对等通信，通常依赖中心化主控转发。

### 1.2 设计愿景

构建一种**统一、模块化、可扩展**的通信架构，使得：

- 任意设备（MCU、SoC、传感器、执行器）遵循同一套协议即可接入网络。
- 设备间支持**对等通信**（Peer-to-Peer），不强制主从关系。
- 实时性与非实时流量在同一网络中**共存且隔离**。
- 物理层可插拔，上层应用完全透明。
- 支持从极简嵌入式节点到高性能计算节点的全谱系部署。
- 支持链式挂载与多级中继，无需依赖专用网关即可实现拓扑柔性扩展。
- 支持多物理链路并行聚合，在资源充足节点上实现带宽叠加与负载均衡。
- 支持裸机与多种 RTOS 的无缝移植，核心协议栈与平台实现完全解耦。
- 提供标准调试服务体系，将调试棒定位为“应用层行为调试工具”，与厂商 JTAG 调试器形成互补。

## 2. 设计目标与原则

### 2.1 设计目标

| 目标 | 描述 |
|------|------|
| **统一协议** | 所有设备使用统一的寻址、路由、服务发现和消息格式。 |
| **物理透明** | 应用层不感知底层是 SPI、CAN FD、TSN 还是无线。 |
| **实时能力表达** | 提供分级 QoS 语义；具体延迟上界由 PHY Profile、调度配置和时间同步能力共同声明，不由统一协议单独保证。 |
| **即插即用** | 设备上电后自动发现、自动注册、自动路由，无需人工配置地址。 |
| **模块化扩展** | 新增设备或物理层仅需实现标准适配接口，不影响现有系统。 |
| **跨域互联** | 支持通过网关实现不同物理域、不同子网之间的无缝通信。 |
| **拓扑柔性** | 支持任意节点作为透明桥接器中继数据，无需专用网关即可动态扩展网络。 |
| **多路径聚合** | 资源充足的节点可同时利用多条异构物理链路通信，实现负载均衡与冗余备份。 |
| **平台无关** | 核心协议栈不依赖任何操作系统或硬件平台，提供标准 PAL 接口供移植。 |
| **调试友好** | 提供标准调试服务，支持非侵入式的运行时行为诊断与参数热更新。 |

### 2.2 设计原则

1. **分层解耦**：严格区分应用层、中间件层、传输层、链路层、物理层，层间通过标准接口交互。
2. **帧格式统一**：定义与物理层无关的统一链路层帧格式，作为全系统的"通用语"。
3. **发布订阅为核心**：采用 Topic 机制解耦生产者和消费者，支持一对多通信。
4. **时间触发优先**：硬实时流量采用时间触发或预留机制，避免仲裁不确定性。
5. **网关即交换机**：网关不仅是协议转换器，更是具备流量调度和 QoS 策略的交换节点。
6. **桥接是备选，不是默认**：透明桥接提供灵活拓扑，但在有直连路径时应优先直连，避免多跳延迟累积。
7. **核心与平台分离**：UMCA 核心不依赖具体 OS、驱动或硬件平台；允许使用明确列入基线的 ISO C 类型与内存操作，所有平台能力通过 PAL 接口注入。
8. **调试不越权**：调试服务仅工作在应用层，不涉及 CPU 内核寄存器操作，与 JTAG/SWD 调试器形成互补而非竞争。

## 3. 总体架构

### 3.1 分层模型

架构采用五层模型，自下而上依次为：

```
┌─────────────────────────────────────────────────────────────┐
│  5. 应用层（Application Layer）                              │
│     统一消息序列化 / 标准服务定义 / 设备模型                   │
├─────────────────────────────────────────────────────────────┤
│  4. 中间件层（Middleware Layer）                             │
│     发布订阅引擎 / 服务发现 / RPC / 数据路由 / QoS 策略        │
├─────────────────────────────────────────────────────────────┤
│  3. 传输层（Transport Layer）                                │
│     分段重组 / 可靠传输 / 流量控制 / 拥塞管理 / 多路径管理      │
├─────────────────────────────────────────────────────────────┤
│  2. 链路层（Link Layer）                                     │
│     统一帧编解码 / CRC 校验 / 地址解析 / 单帧错误检测           │
├─────────────────────────────────────────────────────────────┤
│  1. 物理层（Physical Layer）                                 │
│     可插拔 PHY 适配器（SPI / I2C / CAN FD / TSN / USB / 无线）│
└─────────────────────────────────────────────────────────────┘
```

PAL 是贯穿核心协议栈与平台实现的横切抽象，不属于某一种具体 PHY。UMCA Core 仅依赖 PAL 接口和 PHY Adapter 接口，禁止反向依赖 openvela、FreeRTOS、裸机 HAL 或具体总线驱动。

### 3.2 核心数据流

```
┌─────────┐    publish("/topic")     ┌──────────────┐
│ 应用模块 │ ───────────────────────→ │  中间件层    │
└─────────┘                          │ (Topic 路由) │
                                     └──────┬───────┘
                                            │
                   ┌────────────────────────┼────────────────────────┐
                   ▼                        ▼                        ▼
            ┌─────────────┐          ┌─────────────┐          ┌─────────────┐
            │ 传输层封装   │          │ 传输层封装   │          │ 传输层封装   │
            │ 帧分段/重组  │          │ 帧分段/重组  │          │ 帧分段/重组  │
            └──────┬──────┘          └──────┬──────┘          └──────┬──────┘
                   ▼                        ▼                        ▼
            ┌─────────────┐          ┌─────────────┐          ┌─────────────┐
            │ CAN FD PHY  │          │ TSN PHY     │          │ SPI PHY     │
            └──────┬──────┘          └──────┬──────┘          └──────┬──────┘
                   │                        │                        │
                   ▼                        ▼                        ▼
            [电机驱动节点]            [视觉处理节点]            [IMU 传感器节点]
```

## 4. 各层详细设计

### 4.1 物理层（Physical Layer）

#### 4.1.1 职责
- 提供比特流传输能力。
- 完成电气信号转换、时钟恢复、总线驱动。
- 向上层屏蔽物理介质差异。

#### 4.1.2 PHY 适配器抽象

物理层通过 **PHY Adapter** 接口接入系统。为避免中断上下文、缓冲区生命周期和回调重入产生歧义，MVP 采用由协议任务主动轮询的接口：

| 接口 | 功能 | 语义约束 |
|------|------|----------|
| `init(driver)` | 初始化具体物理接口实例 | 初始化成功后方可收发 |
| `deinit(driver)` | 释放具体实例资源 | 调用后不得继续访问 Adapter实例 |
| `send(driver, data, length)` | 发送一帧完整的 UMCA 字节序列 | 返回后调用者可立即复用发送缓冲区；异步驱动需在内部复制或引用计数 |
| `poll(driver, buffer, capacity, received)` | 轮询接收一帧完整数据 | 由调用者提供缓冲区；Adapter 不保留该缓冲区 |
| `get_mtu(driver)` | 返回单次可承载的最大 UMCA 帧长度 | 包含统一帧头、Payload 和 CRC |
| `get_capabilities(driver)` | 返回带宽、延迟、是否保序及支持的 QoS 能力 | 能力是声明值，不等同于端到端保证 |

- UART 等字节流 PHY 由 Adapter 负责 SOF 搜索、长度检查和失步恢复，并向上层交付完整帧。
- CAN FD、UDP 等报文型 PHY 应保持单个底层报文与单个 UMCA 帧的边界对应；当帧超过 MTU 时由传输层处理分段，MVP 不支持此能力。
- PHY 驱动可在中断中接收底层数据，但不得在中断上下文直接执行 Topic 回调；应先写入固定队列，再由协议任务调用 `poll()` 取出。
- PHY采用`ops + driver`实例描述符；相同操作表可以绑定多个独立driver，Core不得依赖Adapter内部的可变全局状态。

#### 4.1.3 支持的物理层类型

| 物理层 | 适用场景 | 关键特性 |
|--------|----------|----------|
| **SPI** | 板内 SoC-MCU 短距通信 | 全双工、高速、主从或双工模式 |
| **I2C** | 板内低速传感器网络 | 双线、多主仲裁、低速 |
| **CAN FD** | 板间抗干扰通信（汽车、工业） | 差分信号、非破坏性仲裁、高可靠 |
| **TSN / 车载以太网** | 高速骨干网、域间互联 | 时间触发、帧抢占、高带宽 |
| **USB** | 电脑外设、调试接口 | 即插即用、供电一体化、高带宽 |
| **无线（WiFi / BLE / 私有 2.4G）** | 遥控、遥测、免布线场景 | 灵活部署、自组网能力 |

> **设计要点**：极简节点在编译期静态注册 PHY Adapter；资源充足节点可选动态加载。同一设备可同时挂载多个 Adapter，但多路径选择和聚合不属于 MVP。

#### 4.1.4 平台抽象层（PAL，Platform Abstraction Layer，横切抽象）

为实现“核心协议栈不依赖具体 OS、驱动和硬件平台”的目标，UMCA 引入 PAL 层。

**设计原则**：

- UMCA Core 不直接调用 OS、驱动或硬件 API，如 `malloc`、`printf`、`taskENTER_CRITICAL`。
- Core 允许使用 `stdint.h`、`stddef.h`、`stdbool.h` 以及经审计的 `memcpy/memset/memcmp`。
- 所有时间、同步、临界区、日志、断言和可选内存分配能力通过 `ops + user`平台实例描述符注入。
- MVP 默认 `UMCA_USE_DYNAMIC_MEMORY=0`，协议对象、节点表、Topic 表和收发队列全部静态分配。

**需由移植者实现的 PAL 接口**：

| 接口函数 | 功能描述 | 关键语义 |
|----------|----------|----------|
| `time_ms(user)` | 获取单调递增毫秒时间 | 允许回绕；Core 使用无符号差值比较超时 |
| `time_us(user)` | 获取单调递增微秒时间（可选） | 未实现时返回不支持，不得用 RTOS Tick 冒充微秒精度 |
| `critical_enter(user)` | 进入短临界区并返回原状态 | 裸机保存中断使能状态 |
| `critical_exit(user, state)` | 恢复进入前状态 | 支持嵌套，不得无条件开中断 |
| `mutex_lock/unlock(user, mutex)` | 线程级互斥（可选） | mutex由宿主创建并注入；与关中断临界区分离 |
| `alloc/free(user, ...)` | 动态分配（可选） | 仅在 `UMCA_USE_DYNAMIC_MEMORY=1` 时启用 |
| `log(user, level, message)` | 平台日志输出（可选） | Core 不依赖具体 printf 实现 |
| `assert_fail(user, file, line, expr)` | 断言处理（可选） | 生产配置可替换为错误上报或安全停机 |

**裁剪策略（编译时宏）**：
- `UMCA_OS_TYPE`：可选 `UMCA_OS_BAREMETAL`、`UMCA_OS_OPENVELA`、`UMCA_OS_FREERTOS`、`UMCA_OS_RTTHREAD`、`UMCA_OS_ZEPHYR`、`UMCA_OS_LINUX`。
- `UMCA_USE_DYNAMIC_MEMORY`：MVP 固定为 0；后续配置为 1 时必须提供 `alloc/free`。
- `UMCA_SINGLE_THREADED`：为1时允许省略mutex；线程安全配置下mutex由宿主创建并注入，Core不创建或销毁mutex。
- 首期提供 openvela 与 POSIX/Linux PAL；其他平台在对应硬件移植阶段补充。

### 4.2 链路层（Link Layer）

#### 4.2.1 职责
- 定义与物理层无关的统一线级帧格式。
- 实现单帧编解码、长度检查、地址解析与 CRC 校验。
- 向传输层报告 MTU 不足，不在链路层执行分段或重组。

#### 4.2.2 统一帧格式（v0.3.3 MVP Wire Profile）

所有多字节整数统一采用**网络字节序（大端）**。MVP 使用固定 36 字节帧头、0~256 字节 Payload 和 4 字节 CRC32C，固定开销为 40 字节。

| 偏移 | 字段 | 长度 | MVP 定义 |
|------|------|------|----------|
| 0 | SOF / Magic | 2 字节 | 固定为 `0x55 0x4D`（ASCII “UM”） |
| 2 | Version | 1 字节 | MVP 固定为 `0x01` |
| 3 | Header Length | 1 字节 | 从 SOF 至 Payload 前的总帧头长度，MVP 固定为 `36` |
| 4 | Flags | 2 字节 | MVP固定为`0x0000` |
| 6 | Message Type | 1 字节 | DATA / REQUEST / RESPONSE / ANNOUNCE / HEARTBEAT / TEARDOWN / ERROR |
| 7 | QoS | 1 字节 | MVP固定为0；其他值拒绝 |
| 8 | TTL | 1 字节 | 默认 8；仅转发节点递减，值小于等于 1 时不得继续转发 |
| 9 | Reserved | 1 字节 | 必须为 0 |
| 10 | Destination DevID | 8 字节 | 64 位目标设备 ID；`0xFFFFFFFFFFFFFFFF` 表示广播 |
| 18 | Source DevID | 8 字节 | 64 位源设备 ID；0 为无效值 |
| 26 | Topic ID | 4 字节 | Topic 规范化字符串的 FNV-1a 32 位哈希 |
| 30 | Sequence Number | 4 字节 | 按 `<Source DevID, Topic ID>` 独立递增 |
| 34 | Payload Length | 2 字节 | MVP 范围 0~256 |
| 36 | Payload | 可变 | 长度由 Payload Length 给出 |
| 36+N | CRC32C | 4 字节 | 覆盖 Version 字段至 Payload 末尾，不包含 SOF 和 CRC 自身 |

**Flags（MVP）**：整个字段必须为0。ACK_REQUIRED、ACK、ERROR及其他位均未实现；收到非零Flags时拒绝该帧，不得降级处理。

**Message Type 编码（MVP）**：

| 值 | 名称 | 说明 |
|----|------|------|
| `0x00` | DATA | Topic 数据发布 |
| `0x01` | REQUEST | [未实现] 后续RPC使用 |
| `0x02` | RESPONSE | [未实现] 后续RPC使用 |
| `0x03` | ANNOUNCE | 节点与 Topic 宣告 |
| `0x04` | HEARTBEAT | 节点存活心跳 |
| `0x05` | TEARDOWN | 节点主动下线 |
| `0x06` | ERROR | [未实现] MVP仅使用本地错误码和统计 |
| `0x07~0xFF` | Reserved | 未定义，MVP 接收端返回不支持 |

**CRC32C 参数**：Castagnoli 多项式，反射多项式 `0x82F63B78`，初值 `0xFFFFFFFF`，结果异或 `0xFFFFFFFF`。

**DevID 规则**：

- 优先使用生产写入的稳定 64 位 ID。
- 其次使用芯片唯一 ID 经稳定哈希得到 64 位值。
- 随机临时 ID 仅允许用于仿真和演示；检测到冲突时节点停止发送全部UMCA帧，只保留接收和本地诊断，直到重新配置。
- 组播地址空间在后续版本定义，MVP 仅支持单播和全局广播。

**Topic ID 规则**：

1. Topic必须以`/`开头并大小写敏感；MVP只允许ASCII字母、数字、`_`、`-`和`.`作为路径段字符。
2. 除根 Topic 外不得以 `/` 结尾，不允许空路径段、`.` 或 `..`。
3. 对规范化后的完整字符串计算 FNV-1a 32 位哈希，offset basis 为 `0x811C9DC5`，prime 为 `0x01000193`。
4. 服务发现宣告同时携带 Topic ID 和 Topic 字符串；若同一网络发现同 ID 不同字符串，相关 Topic 标记为冲突并拒绝路由。

**Sequence Number 语义**：

- 序列号不是全网全局计数器，而是按 `<Source DevID, Topic ID>` 维护的 32 位无符号计数器。
- MVP 用于重复帧检测、丢包统计和日志追踪；自然回绕按无符号序列比较处理。
- ANNOUNCE、HEARTBEAT和TEARDOWN携带非零32位Boot ID；只有ANNOUNCE出现新的Boot ID时建立新启动会话并清除旧Sequence历史，HEARTBEAT和TEARDOWN只作用于匹配当前Boot ID的会话。
- 节点启动后必须先发送ANNOUNCE，再发送普通业务DATA。
- 乱序重排仅在后续多路径传输 Profile 中启用。

#### 4.2.3 分段与重组

分段和重组统一由**传输层**负责，链路层只处理单帧。

- MVP 不支持分段；`UMCA_MVP_MAX_PAYLOAD=256`。
- 单个 PHY 可承载的有效 Payload 上限为 `min(256, PHY_MTU - 40)`。
- 超过有效上限时返回 `UMCA_ERR_PAYLOAD_TOO_LARGE`，不得静默截断。
- CAN FD 的 64 字节 MTU 在 MVP 中最多直接承载 24 字节 Payload；更大消息需等待后续分段 Profile。

#### 4.2.4 解码校验顺序与错误处理

接收端必须按以下顺序校验，任一步失败均不得将 Payload 递交上层：

1. 检查 SOF、最小帧长和接收缓冲区边界。
2. 检查 Version；MVP 仅接受 `0x01`。
3. 检查 Header Length；Version 1 仅接受 `36`。
4. 检查 Reserved 字段和未定义 Flags 是否为 0。
5. 检查 Payload Length 是否小于等于 256，且实际帧长等于 `36 + Payload Length + 4`。
6. 校验 CRC32C。
7. 检查 Source DevID、Message Type、Topic ID 和本地容量限制。

MVP 至少定义以下错误：`UMCA_ERR_INVALID_ARG`、`UMCA_ERR_BAD_MAGIC`、`UMCA_ERR_UNSUPPORTED_VERSION`、`UMCA_ERR_BAD_HEADER`、`UMCA_ERR_PAYLOAD_TOO_LARGE`、`UMCA_ERR_LENGTH_MISMATCH`、`UMCA_ERR_CRC`、`UMCA_ERR_UNSUPPORTED_TYPE`、`UMCA_ERR_CAPACITY` 和 `UMCA_ERR_TOPIC_COLLISION`。

---

### 4.3 传输层（Transport Layer）

#### 4.3.1 职责
- 端到端的可靠传输控制（可选）。
- 分段与重组管理。
- 流量控制与拥塞避免。
- 多路径管理与负载均衡。

#### 4.3.2 传输模式

| 模式 | 适用场景 | 机制 |
|------|----------|------|
| **不可靠报文（Datagram）** | 高频传感器数据、实时控制 | 无确认、无重传、最低延迟 |
| **可靠报文（Reliable Message）** | 配置参数、固件指令 | 确认应答 + 超时重传 |
| **请求-响应（RPC）** | 远程调用、状态查询 | 请求帧 + 响应帧配对，支持超时与幂等性 |
| **流式传输（Stream）** | 日志、固件 OTA | 滑动窗口 + 流量控制 |

#### 4.3.3 路由与转发

传输层维护一张**路由表**，记录到达各目标地址的下一跳和物理接口。路由表通过以下方式建立：

- **直连发现**：通过链路层直接可达的设备自动注册。
- **网关通告**：网关周期性发布可达子网信息。
- **动态学习**：通过数据帧的源地址反向学习路径。

#### 4.3.4 多路径传输与通道绑定（Channel Bonding）

资源充足的节点（如 SoC、域控）可启用此高级特性，实现多总线并行通信。

- **工作原理**：
  1. **链路聚合**：节点将多个活动的 PHY Adapter（如 CAN FD + SPI + TSN）绑定为一个逻辑通道。
  2. **负载分担**：传输层根据各 PHY 的实时带宽和延迟权重，将数据流切分为子帧，分发到不同物理链路。
  3. **顺序重组**：接收端按逻辑数据流维护重组缓冲区，使用该流的 Sequence Number 将乱序子帧重排后递交上层。
- **轻量化开关**：该特性为编译时可选（`UMCA_CHANNEL_BONDING`），默认关闭。极简节点（MCU）编译时无需包含此模块，零额外开销。
- **故障容错**：当某条物理链路中断时，流量自动切换到其他可用链路，对上层应用完全透明。

---

### 4.4 中间件层（Middleware Layer）

#### 4.4.1 职责
- 实现**发布订阅（Publish/Subscribe）**语义。
- **服务发现**：自动发现网络中的设备、Topic 和服务。
- **Topic 路由**：根据订阅关系将消息分发到感兴趣的节点。
- **QoS 策略执行**：根据消息 QoS 等级选择物理通道和调度策略。
- **RPC 框架**：提供远程过程调用能力。

#### 4.4.2 发布订阅机制

- **Topic**：应用层使用层级字符串命名空间（如 `/sensors/imu/raw`）；线级帧使用其 FNV-1a 32 位 Topic ID。
- **Publisher**：向 Topic 发布消息，不感知订阅者数量和身份。
- **Subscriber**：向 Topic 注册订阅，通过协议任务上下文中的回调接收消息；不得在 PHY 中断中直接执行回调。
- **Broker-less 模式**：MVP 默认模式，节点依据本地订阅表和服务发现目录直连转发。
- **Broker 模式**：后续可选能力，用于跨网关复杂路由。
- **静态资源上限**：MVP 默认最多 8 个发现节点、16 个本地 Topic、每节点 8 个宣告 Topic；具体值可编译配置但不得动态扩容。

#### 4.4.3 服务发现协议

MVP 服务发现仅实现 `ANNOUNCE`、`HEARTBEAT` 和 `TEARDOWN`，采用无中心广播发现：

1. **宣告（ANNOUNCE）**：节点广播DevID、Boot ID、节点能力、最多8组`<Topic ID, Topic字符串, 发布/订阅属性>`。
2. **监听（Listening）**：接收宣告并更新固定容量节点表，同时检查 DevID 和 Topic ID 碰撞。
3. **心跳（HEARTBEAT）**：默认每 5 秒发送一次；连续 3 个周期未收到则将节点标记为离线。
4. **注销（TEARDOWN）**：正常下线时发送带当前Boot ID的注销帧；接收方只注销匹配当前会话的节点记录。

MVP 约束：

- 宣告内容必须在单帧 MTU 内完成；超过 8 个 Topic 的节点仅宣告核心 Topic。
- 节点启动后必须先发送ANNOUNCE；未知DevID的HEARTBEAT不创建节点表项。
- Reachable List、分页目录、桥接路径和调试特权标记保留到后续 Profile。
- 时间参数均通过编译配置定义，超时比较必须正确处理毫秒计数器回绕。

**MVP 发现消息 Payload 编码**（多字节整数均为大端）：

| 消息 | Payload 格式 |
|------|--------------|
| ANNOUNCE | `capabilities:u32`、`boot_id:u32`、`topic_count:u8`，随后为若干Topic Entry |
| Topic Entry | `topic_id:u32`、`direction:u8`、`name_length:u8`、`name:ASCII bytes` |
| HEARTBEAT | `boot_id:u32`、`uptime_ms:u32`、`status:u8` |
| TEARDOWN | `boot_id:u32`、`reason:u8` |

- `direction`：位 0 表示 Publisher，位 1 表示 Subscriber，其余位必须为 0。
- 单个 Topic 名称最长 63 字节；`topic_count` 最大为 8，但编码后的完整 ANNOUNCE Payload 仍不得超过 256 字节。
- `capabilities` 在 MVP 中仅定义位 0 `CAP_PUBSUB`；其余位必须为 0。
- `boot_id`必须非零，同一次运行期间保持不变；同一DevID更换Boot ID表示节点进入新会话。
- OFFLINE节点表项允许被新节点确定性复用，优先空表项，其次最早进入OFFLINE的表项。
- ANNOUNCE、HEARTBEAT 和 TEARDOWN 使用保留的系统 Topic ID `0x00000000`；普通业务 Topic 不得使用该值。

#### 4.4.4 设备模型抽象

每个设备在逻辑上是一个**服务容器**，包含若干标准服务接口：

- `ParameterService`：参数读写（配置管理）。
- `TelemetryService`：遥测数据发布（传感器）。
- `ControlService`：控制指令接收（执行器）。
- `LogService`：日志发布与查询。
- `DiagnosticService`：诊断与自检。
- `DebugService`：标准调试服务（详见 4.4.6）。

#### 4.4.5 服务发现中的"可达范围"宣告

在设备宣告帧中，除了 DevID 和 Topic 列表外，可选携带 **"可达设备列表"（Reachable List）**。例如，桥接节点会宣告："我直连了设备 A，通过我可达设备 B 和设备 C"。其他节点收到后，可动态建立多跳路由表，减少对中心网关的依赖。

#### 4.4.6 标准调试服务（DebugService）

##### 定位与设计哲学

UMCA 调试服务**不是** JTAG/SWD 调试器的替代品，而是**互补品**：

| 维度 | JTAG/SWD 调试器 | UMCA DebugService |
|------|----------------|-------------------|
| 调试层级 | 硬件/内核级（寄存器、指令） | 应用/网络级（Topic、参数、行为） |
| 侵入性 | **侵入式**（暂停 CPU 执行） | **非侵入式**（目标全速运行） |
| 适用场景 | 烧录固件、硬件断点、启动代码调试 | 运行时调参、通信行为诊断、故障复现 |
| 物理依赖 | 需要 JTAG/SWD 引脚 | 使用现有通信总线（CAN/SPI/TSN/无线） |

**核心原则**：调试服务**绝不强制**任何节点开放内部寄存器。节点**自愿实现** DebugService，并在编译时通过宏 `UMCA_ENABLE_DEBUG` 决定是否包含该服务。MVP 固定 `UMCA_ENABLE_DEBUG=0`；在挑战响应算法、重放保护、令牌生命周期和权限模型冻结前，不实现远程数据注入、参数写入或复位命令。生产固件可完全裁剪。

##### 调试服务 API 定义

| 方法 | 功能 | 安全约束 |
|------|------|----------|
| `ping()` | 探测节点是否存活并返回运行状态 | 无限制，所有节点默认响应 |
| `get_param(key)` | 读取指定参数名对应的值（如 PID_Kp） | 节点自主决定暴露哪些参数 |
| `set_param(key, value)` | 热更新指定参数 | 节点校验数值范围合法性，非法则拒绝 |
| `subscribe_topic(topic)` | 临时订阅某 Topic（调试器动态监听） | 仅限节点已发布的 Topic |
| `inject_data(topic, payload)` | **注入虚拟数据**到指定 Topic | 模拟传感器故障测试系统容错，节点可在应用层过滤 |
| `get_topic_list()` | 获取节点当前发布的所有 Topic | 只读，无副作用 |
| `get_service_list()` | 获取节点支持的所有服务 | 只读，无副作用 |
| `reset_target()` | 软复位节点（需物理按键确认） | **高危**：需帧头携带一次性令牌（OTP），由节点板载按键生成 |

##### 调试会话安全机制

- **特权宣告**：调试棒在宣告帧中携带 `Capability: FLAG_DEBUG_PRIVILEGE`。
- **握手授权**：被调试节点**默认拒绝**所有调试命令。调试棒首次发起调试请求时，需完成握手（调试棒发送挑战码，节点回复预期响应，或等待物理按键确认）。
- **会话绑定**：一旦握手成功，节点记录调试棒的 `Source DevID`。后续调试命令必须来自同一 ID，否则忽略。

#### 4.4.7 远程服务授权与访问控制（ACL）

为支持跨设备服务调用（如设备 A 调用设备 B 的电机控制），中间件层提供轻量级 ACL 机制：

- **授权表**：每个设备本地维护一张 `<调用者 ID, 允许的服务列表>` 白名单。
- **调用流程**：远程调用帧携带调用者 ID，接收方校验 ACL，通过则执行，拒绝则回复错误码。
- **极简模式**：ACL 校验为可选特性。比赛仿真可在隔离网络中显式启用“信任同网段”模式，但该模式不得作为生产默认值；MVP 不实现远程高危服务。

### 4.5 应用层（Application Layer）

#### 4.5.1 职责
- 定义标准消息 schema（推荐使用 Protobuf / nanopb / FlatBuffers）。
- 实现业务逻辑，调用中间件层 API 进行通信。
- 完全无需关心底层物理介质。

#### 4.5.2 标准消息定义

系统预定义一系列标准消息类型，覆盖常见嵌入式场景：

- **传感器类**：IMU、轮速、激光雷达点云、摄像头帧、超声波测距。
- **执行器类**：电机速度/力矩指令、舵机角度、PWM 占空比。
- **系统类**：心跳、错误码、固件版本、电源状态、温度。
- **控制类**：PID 参数、模式切换、急停指令、校准指令。
- **调试类**：参数读写请求/响应、Topic 注入请求、节点状态查询。

> **扩展机制**：用户可自定义消息类型，通过 Topic/Service 命名空间注册，并映射为统一的 32 位 Topic ID，不影响标准消息。

## 5. 网络拓扑与设备角色

### 5.1 拓扑结构

架构支持多种拓扑，根据场景灵活选择：

- **总线型**：CAN FD 总线挂接多个节点，简单可靠。
- **星型**：TSN 交换机为中心，各节点独立链路，无冲突。
- **树型**：多级网关/交换机级联，适合大规模系统。
- **混合型**：同一系统中同时存在总线域和交换域，通过网关互联。
- **链式拓扑（Daisy-Chain）**：设备 A → 设备 B（桥接） → 设备 C，无需交换机或网关，依靠节点自身的多 PHY 接口实现级联，特别适合接口数量有限或现场布线受限的场景。

### 5.2 设备角色

| 角色 | 能力 | 典型设备 |
|------|------|----------|
| **普通节点（Node）** | 发布/订阅 Topic，响应 RPC | 传感器、执行器、单功能 MCU |
| **网关（Gateway）** | 跨物理层转发、QoS 映射、子网隔离、协议转换 | 域控制器、通信枢纽 MCU |
| **透明桥接节点（Transparent Bridge）** | 拥有 ≥2 个 PHY 接口，不解析 Payload，仅基于 DevID 做链路层存储转发。无路由表维护负担，延迟极低（纯 DMA 搬运） | 带屏幕的交互模块、带额外 SPI/CAN 口的传感器 Hub |
| **主控（Host）** | 运行复杂算法、聚合多源数据、下发决策 | SoC、工控机、飞控板 |
| **监视器（Monitor）** | 只接收不发送（日志、调试） | PC 上位机、手机 App |
| **调试器（Debugger）** | 具备调试特权，可动态订阅、注入数据、热更新参数 | UMCA 调试棒、PC 调试上位机 |

> **去中心化设计**：系统不强制存在"主控"。纯 Node 之间可直接对等通信，Host 仅作为功能更强的 Node 存在。

## 6. 服务质量（QoS）体系

### 6.1 QoS 分级

系统定义四级 QoS 语义，用于表达业务需求和选择调度策略。表中数值是**目标能力**，只有具体 PHY Profile、时钟同步、驱动调度和负载条件同时满足时，才能声明相应端到端保证。

| 等级 | 名称 | 目标延迟 | 目标抖动 | 目标可靠性 | 典型物理层策略 |
|------|------|----------|----------|------------|----------------|
| **QoS-3** | 关键控制（Critical Control） | < 100μs | < 10μs | 99.999% | TSN 时间触发窗或专用预留通道 |
| **QoS-2** | 实时数据（Real-time Data） | < 1ms | < 100μs | 99.99% | TSN 速率约束或高优先级总线 |
| **QoS-1** | 可靠传输（Reliable Delivery） | < 10ms | 不敏感 | 99.9%（带重传） | 可靠报文、确认和有限重试 |
| **QoS-0** | 尽力而为（Best Effort） | 不保证 | 不敏感 | 不保证 | 任何可用通道 |

MVP能力固定为QoS-0。收到QoS-1~3帧时必须拒绝，不得解析后降级交付或转发；这些等级只在后续Profile实现并重新冻结后启用。

### 6.2 QoS 保障机制

#### 6.2.1 时间触发（Time-Triggered）

- 适用于 QoS-3 和 QoS-2。
- 全网通过 gPTP（或简化版时间同步协议）维护全局时钟。
- 关键 Topic 在发送端和交换机端预留**专属时间窗口**。
- 时间窗口内禁止其他流量抢占，确保零竞争。

#### 6.2.2 优先级仲裁（Priority Arbitration）

- 适用于 CAN FD 等事件触发总线。
- 通过 Topic ID 或显式调度表映射到 CAN ID 优先级。
- **仅作为时间触发的补充**，不单独用于 QoS-3 流量。

#### 6.2.3 流量整形（Traffic Shaping）

- 网关节点执行**令牌桶 / 漏桶算法**。
- 限制 QoS-0 和 QoS-1 流量的突发，防止冲击实时通道。

#### 6.2.4 冗余与热备份

- QoS-3 流量支持双通道冗余发送（如 TSN 双链路）。
- 接收端通过序列号去重，确保即使单链路故障也不丢关键帧。

## 7. 网关与域间通信

### 7.1 网关定位

网关是架构中的关键组件，承担以下职责：

1. **协议桥接**：将统一帧格式在不同物理层之间转换（如 CAN FD ↔ TSN）。
2. **路由聚合**：维护跨子网路由表，实现不同域之间的消息转发。
3. **QoS 映射**：将源域的 QoS 等级映射到目标域的等效等级（如 CAN FD 优先级 ↔ TSN VLAN PCP）。
4. **流量隔离**：通过防火墙策略阻止非法跨域访问，保障安全。
5. **时间同步中继**：在跨域场景中中继时间同步信号，维持全局时钟一致性。

### 7.2 域（Domain）划分

系统将网络划分为若干**域**，每个域内部物理层和拓扑相对统一：

```
┌─────────────────────────────────────────────────────────────┐
│                      骨干域（Backbone）                       │
│                 TSN / 高速以太网交换网络                      │
│         ┌─────────────┐    ┌─────────────┐                  │
│         │   网关 A     │    │   网关 B     │                  │
│         │ (域控制器)   │    │ (域控制器)   │                  │
│         └──────┬──────┘    └──────┬──────┘                  │
└────────────────┼──────────────────┼──────────────────────────┘
                 │                  │
        ┌────────┴────────┐  ┌─────┴──────────┐
        ▼                 ▼  ▼                ▼
   ┌──────────┐      ┌──────────┐      ┌──────────┐
   │ 动力域    │      │ 感知域    │      │ 座舱域    │
   │ CAN FD   │      │ TSN      │      │ USB/WiFi │
   │ 总线拓扑  │      │ 星型拓扑  │      │ 混合拓扑  │
   └──────────┘      └──────────┘      └──────────┘
```

### 7.3 跨域通信流程

1. 源节点在域 A 内发布 Topic。
2. 网关 A 订阅该 Topic（或根据路由策略被动监听）。
3. 网关 A 将帧转换为域 B 的物理层格式，保持 QoS 等级。
4. 网关 B（或同一网关的另一接口）在域 B 内转发。
5. 域 B 内的订阅节点接收消息。

> **透明性**：源节点和订阅节点均不感知对方位于不同域。

### 7.4 轻量级透明桥接（Lightweight Transparent Bridging）

#### 7.4.1 定义与定位

透明桥接是 UMCA 中一种比网关更轻量的中继方式，适用于以下场景：

- 设备 A 的主控接口已用完，但设备 A 的屏幕模块还有空闲 SPI 接口，设备 B（电机控制板）通过屏幕模块接入主控。
- 多个传感器以菊花链方式串联后，统一接入域控的一个 CAN FD 接口。

#### 7.4.2 工作机制

1. **路径发现**：屏幕模块上电后，在宣告帧中携带 `[Bridge]` 标记，并列出自己能直达的设备 ID（如主控 A）。
2. **透明转发**：设备 B 发送目标为"主控 A"的帧给屏幕模块。屏幕模块的链路层执行以下操作：
   - 不解析 Payload（不解码服务 ID/Topic）。
   - 仅将帧头中的源/目标链路层地址保持不变，物理层封装由接收 PHY 切换为发送 PHY。
   - 直接将帧推送到通往主控 A 的 PHY 队列。
3. **反向学习**：主控 A 回复设备 B 时，其路由表自动学习到"去往设备 B 需经由屏幕模块"。

#### 7.4.3 轻量化保证

- **小型转发表**：桥接节点无需维护完整动态路由协议，但必须维护有界的出口映射缓存；容量由实现配置，不固定承诺小于 256 字节。
- **零拷贝目标**：具备 DMA 和兼容缓冲区布局的平台可使用描述符链减少复制；“< 50μs”仅作为特定 100Mbps 硬件 Profile 的验证目标，不是通用保证。
- **环路预防**：转发节点仅在 TTL 大于 1 时执行转发，并在发出前减 1；TTL 小于等于 1 的帧不得继续转发。

#### 7.4.4 与网关的区别

| 维度 | 网关 | 透明桥接节点 |
|------|------|-------------|
| 处理层级 | 应用层（可修改 Payload、QoS 映射） | 链路层（纯转发） |
| 资源消耗 | 较高（需运行路由协议、QoS 队列管理） | 极低（仅需 DMA 搬运） |
| 适用节点 | 域控、高性能 MCU | 任意带 ≥2 个 PHY 的节点（含低端 MCU） |

## 8. 扩展性设计

### 8.1 物理层扩展

新增物理层仅需实现标准 PHY Adapter 接口，无需修改上层代码。例如：

- 未来引入 **10BASE-T1S**（单对以太网总线）时，只需新增一个 Adapter。
- 上层中间件通过 `get_capabilities()` 自动识别新物理层的带宽和 QoS 能力。

### 8.2 服务扩展

- 新增设备类型时，定义新的 Topic/Service 命名空间和消息 Schema 即可。
- 标准服务库通过版本号管理，向后兼容。
- 支持运行时动态加载服务描述（JSON/二进制描述文件）。

### 8.3 拓扑扩展

- 系统支持从 2 个节点的极简系统扩展到数百节点的分布式系统。
- 小规模：直连总线，无网关。
- 中规模：单级网关 + 多子网。
- 大规模：多级网关级联 + 冗余骨干网。

### 8.4 安全扩展（预留）

- 帧格式预留加密标识位，未来可叠加 AES-128/256 载荷加密。
- 支持设备证书认证和 Topic 级访问控制列表（ACL）。
- 网关可作为安全边界，执行深度包检测（DPI）。

## 9. 典型应用场景映射

### 9.1 智能车 / 机器人

| 模块 | 物理层 | QoS 等级 | 通信模式 |
|------|--------|----------|----------|
| 电机驱动 × 4 | CAN FD | QoS-3 | Pub/Sub `/cmd/vel_*` |
| 底盘 IMU | SPI + CAN FD | QoS-2 | Pub `/sensors/imu` |
| 激光雷达 | TSN | QoS-2 | Pub `/sensors/lidar` |
| 视觉 SoC | TSN | QoS-1 | Pub `/sensors/camera` |
| 主控域控 | TSN | QoS-1/2 | Sub + RPC |
| 调试上位机 | USB/WiFi | QoS-0 | Sub `/log/*` |

**链式挂载示例**：

- 主控 Jetson 的 CAN 口接了 4 个电机，SPI 口已用于屏幕。
- 新增一个超声波雷达模块（只有 SPI 口），此时将雷达插入屏幕模块的空闲 SPI 口。
- 效果：屏幕模块自动作为透明桥，将雷达数据转发给 Jetson 主控，无需拔掉任何现有设备，代码零修改。

### 9.2 无人机

| 模块 | 物理层 | QoS 等级 | 通信模式 |
|------|--------|----------|----------|
| 飞控 MCU | CAN FD / 私有 2.4G | QoS-3 | Pub/Sub `/flight/attitude` |
| 电调 × N | CAN FD | QoS-3 | Sub `/cmd/motor_*` |
| GPS/磁力计 | UART/I2C | QoS-2 | Pub `/sensors/gps` |
| 图传模块 | 私有 5.8G / WiFi | QoS-0 | Stream `/video/fpv` |
| 地面站 | 无线 | QoS-0/1 | RPC + Telemetry |

### 9.3 智能家电

| 模块 | 物理层 | QoS 等级 | 通信模式 |
|------|--------|----------|----------|
| 主控面板 | WiFi / BLE Mesh | QoS-1 | RPC + Pub |
| 温控传感器 | BLE / I2C | QoS-1 | Pub `/sensors/temp` |
| 压缩机驱动 | CAN FD / UART | QoS-2 | Sub `/cmd/compressor` |
| 手机 App | WiFi | QoS-0 | RPC `/config/*` |

### 9.4 电脑外设

| 模块 | 物理层 | QoS 等级 | 通信模式 |
|------|--------|----------|----------|
| 键盘/鼠标 | USB HID | QoS-2 | Pub `/input/keyboard` |
| 游戏手柄 | USB / 无线 | QoS-2 | Pub `/input/joystick` |
| 扩展坞 Hub | USB + TSN | QoS-1 | Gateway + Stream |
| 显示器 | DP/USB-C | QoS-0 | Stream `/video/display` |

### 9.5 多调试棒协同调试场景

**场景**：大型机器人系统包含 CAN 动力域 + SPI 传感器域 + 无线遥控域。

- **逻辑聚合模式**：PC 同时连接调试棒 A（CAN 接口）和调试棒 B（SPI 接口），上位机将其聚合为一个“超级调试器”。用户在上位机同时监控电机 Topic 和 IMU Topic。
- **透传中继模式**：主调试棒 A 插 PC，子调试棒 B 无线放置在高压电机旁（物理隔离）。A 转发上位机指令给 B，B 采集电机数据回传。PC 上位机看到的是完整的远程调试视图。

## 10. 演进路线

### Phase 1：最小可行产品（MVP）

- 实现v0.3.3 MVP Wire Profile、CRC32C、严格长度校验和静态内存配置。
- 提供 openvela 与 POSIX/Linux PAL。
- 实现 Loopback PHY，并定义 UART PHY 接口；硬件到位后验证 UART。
- 实现基础 Pub/Sub、ANNOUNCE/HEARTBEAT/TEARDOWN 和固定容量节点表。
- QoS 字段保留但仅执行 QoS-0；Sequence 用于去重、丢包统计和追踪。
- 不实现分段、RPC、多路径、网关、DebugService、ACL 或加密。
- 在 2~4 个虚拟节点上验证“传感器发布—Agent 决策—执行器反馈”闭环。

### Phase 2：中间件完善

- 完善服务发现，增加分页目录、Reachable List 和桥接路径学习。
- 实现 RPC 框架和参数服务。
- 支持网关和跨域转发。
- 引入 QoS-1 / QoS-2 分级。

### Phase 3：实时性与规模化

- 引入 TSN / 时间同步支持。
- 实现 QoS-3 硬实时通道。
- 支持 50+ 节点的大规模网络。
- 引入冗余链路和故障切换。

### Phase 4：生态与标准化

- 发布标准服务库和代码生成工具。
- 提供 PC 端可视化调试工具。
- 引入安全加密和认证机制。
- 推动社区贡献第三方 PHY Adapter。

## 11. 风险与权衡

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 统一帧格式引入额外开销 | 小帧场景效率降低 | 允许物理层压缩/映射（如 CAN ID 承载部分地址） |
| 时间同步精度不足 | 硬实时抖动超标 | 采用硬件时间戳 + gPTP，必要时用 FlexRay 替代 |
| 网关成为瓶颈 | 跨域延迟增加 | 网关专用硬件加速，支持多队列并行转发 |
| 生态兼容性 | 难以对接现有 CANopen/Modbus 设备 | 提供协议转换网关和兼容层 |
| 复杂度上升 | 小系统负担过重 | 支持编译裁剪，极简场景可退化为基础总线协议 |
| **PAL 移植工作量** | 不同 OS/硬件平台适配耗时 | 提供主流平台参考实现，社区共建 |
| **调试服务安全风险** | 调试特权可能被滥用 | MVP 默认关闭；后续冻结认证、重放保护和权限模型后再启用 |
| **MVP 帧头开销** | 40 字节固定开销压缩 CAN FD 有效 Payload | 小控制消息直传；大消息等待传输层分段 Profile |
| **Topic 哈希碰撞** | 不同 Topic 映射到相同 32 位 ID | 服务发现同时宣告字符串，检测冲突后拒绝路由 |
| **静态资源上限** | 节点或 Topic 超过编译容量时无法接入 | 明确返回容量错误，按目标硬件调整编译配置 |

## 12. 术语表

| 术语 | 定义 |
|------|------|
| **UMCA** | Unified Modular Communication Architecture，本架构代号 |
| **PHY Adapter** | 物理层适配器，封装具体总线差异 |
| **Topic** | 发布订阅机制中的逻辑信道，采用层级命名 |
| **QoS** | Quality of Service，服务质量等级 |
| **TTS** | Time-Triggered Send，时间触发发送 |
| **gPTP** | generalized Precision Time Protocol，广义精确时间同步协议 |
| **Domain** | 域，具有统一物理层特性的子网络 |
| **Gateway** | 网关，跨域通信和协议转换的枢纽节点 |
| **透明桥接节点（Transparent Bridge）** | 拥有 ≥2 个 PHY 接口，在链路层进行帧转发的中继节点，不解析上层协议，开销极低。 |
| **通道绑定（Channel Bonding）** | 将多个异构物理链路聚合为一个逻辑通道，实现带宽叠加和负载均衡。 |
| **PAL** | Platform Abstraction Layer，平台抽象层，隔离 OS 与硬件差异 |
| **调试器（Debugger）** | 具备调试特权的节点，可动态订阅、注入数据、热更新参数 |
| **调试服务（DebugService）** | UMCA 标准应用层调试接口，用于非侵入式运行时诊断 |
| **DevID** | 64 位设备标识；MVP 支持单播和全局广播 |
| **Topic ID** | 规范化 Topic 字符串的 FNV-1a 32 位哈希 |
| **MVP Wire Profile** | v0.3.3冻结的固定帧编码、严格能力边界、CRC和资源约束 |

## 13. 附录：架构设计原则速查

1. **统一帧格式是底线**：任何物理层必须能承载统一帧格式的语义。
2. **业务优先通过 Topic 解耦**：应用数据不绑定具体订阅节点；管理、发现和后续 RPC 仍可使用 DevID 定向通信。
3. **实时性不靠仲裁**：QoS-3 流量必须走时间触发或预留通道。
4. **网关是交换机，不是瓶颈**：网关应具备硬件级转发能力。
5. **扩展不修改核心**：新增物理层或服务只需外围适配，不动中间件内核。
6. **桥接是备选，不是默认**：透明桥接提供灵活拓扑，但在有直连路径时应优先直连，避免多跳延迟累积。
7. **核心与平台分离**：UMCA Core 不依赖具体 OS、驱动或硬件平台，PAL 接口隔离平台差异。
8. **调试不越权**：调试服务仅限应用层行为诊断，不涉及 CPU 内核寄存器操作。

## 14. v0.3.3 MVP 实现约束速查

| 项目 | 固定约束 |
|------|----------|
| 字节序 | 网络字节序（大端） |
| 固定帧头 | 36 字节 |
| 固定总开销 | 40 字节（帧头 36 + CRC32C 4） |
| DevID | 64 位 |
| Topic ID | FNV-1a 32 位 |
| Sequence | 32 位，按 `<Source DevID, Topic ID>` 递增 |
| Boot ID | 32位非零启动会话标识，随ANNOUNCE、HEARTBEAT和TEARDOWN发送 |
| Payload | 0~256 字节；不支持分段 |
| CRC | CRC32C Castagnoli |
| 内存 | 静态分配，`UMCA_USE_DYNAMIC_MEMORY=0` |
| 最大帧长 | 296 字节（帧头 36 + Payload 256 + CRC 4） |
| 默认节点表 | `UMCA_MAX_NODES=8` |
| 默认本地 Topic 表 | `UMCA_MAX_TOPICS=16` |
| 每节点宣告 Topic | `UMCA_MAX_TOPICS_PER_NODE=8` |
| 默认收发队列 | RX 4 帧、TX 4 帧，编译期可调 |
| PAL | `ops + user + mutex`注入；首期支持openvela、POSIX/Linux |
| PHY | `ops + driver`多实例；Loopback实现，UART定义并待硬件验证 |
| 服务发现 | ANNOUNCE、HEARTBEAT、TEARDOWN |
| Flags | 固定为0；ACK和ERROR不实现 |
| QoS | 固定为0；其他值拒绝，不静默降级 |
| Topic字符集 | 可移植ASCII子集 |
| DebugService | `UMCA_ENABLE_DEBUG=0` |
| 安全/ACL | MVP 不实现远程高危服务 |
| 验证规模 | 2~4 个虚拟节点 |

**MVP 验收条件**：

1. 两个以上虚拟节点通过 Loopback PHY 互相发现。
2. 传感器节点发布 Topic，订阅者收到并校验 Sequence 与 CRC。
3. CRC 错误、非法长度、未知版本和容量超限均返回明确错误。
4. 心跳超时后节点被标记离线，TEARDOWN 可立即注销。
5. ai_agent 可通过独立适配层查询传感器并控制虚拟执行器。
6. 温度等阈值事件能够触发“主动感知—智能决策—执行反馈”闭环。
7. UMCA Core 不直接包含 openvela、POSIX、UART 或 ai_agent 头文件。
8. 同一DevID更换Boot ID后可立即建立新会话并接受新的Sequence。
9. CRC、Topic ID和完整帧编码与协议固定测试向量逐字节一致。
